# Cache policy and focused firmware support

Status: required work agreed on 2026-10-20; implementation has not started. The project remains primarily frontend. The user permits necessary small firmware changes and added endpoints, and explicitly requests ETags and improved caching with `no-cache`. Stage 00b implements the initial support; feature stages may add justified compatible extensions.

## Planned HTTP policy

The current firmware gives many static files, including HTML, a 12-hour freshness lifetime and does not implement ETag validation. Replace that policy deliberately while preserving both UIs, their URLs, setup interception, authentication and integration contracts.

| Resource | Planned cache behavior | Purpose |
| --- | --- | --- |
| Alternative HTML entry and legacy HTML pages | `Cache-Control: private, no-cache` and a valid ETag where file-backed | Validate before reuse, return an unchanged page without resending its body |
| Mutable/unhashed static JS, CSS, help and static images | `private, no-cache` plus ETag | Correct updates even when the URL has not changed |
| Verified content-hashed alternative assets | Long-lived private caching, with `immutable` appropriate only for truly immutable URLs; retain ETag | Avoid repeat transfers/requests while the asset URL uniquely identifies its bytes |
| Version/build metadata | `private, no-cache` plus reliable validator when applicable | Detect installed build changes |
| Live readings/status/virtual images, config/secrets, log tails/listings and mutation responses | Explicit fresh-response policy, initially `no-store` where appropriate | Prevent stale device state or cached operation results; no long static lifetime |
| Setup/error/recovery HTML generated by firmware | `no-store` unless a complete representation-specific validation scheme is implemented | Never validate a recovery page against the static index file's tag |

This table is the planned implementation policy, not a claim about current headers. Consider dynamic-route header changes individually to preserve external clients; document covered routes and defaults. Do not cache mutation-by-GET responses as ordinary static content. Existing `/fileserver` downloads need classification too: mutable configuration/history images must not inherit hashed-asset caching.

`no-cache` allows a browser to store a response but requires validation before reuse. `no-store` disallows storage; it is a different policy. Private caching confines reuse to the browser cache. These distinctions follow [RFC 9111, response cache directives](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2).

## Conditional GET behavior

1. Apply Basic authentication and existing routing/setup/error decisions first.
2. Select the actual response representation, including a `.gz` sibling where served. Look up a trustworthy validator for those exact bytes.
3. Send a properly quoted ETag on normal cacheable file responses. Handle `If-None-Match` according to HTTP semantics, including lists, weak comparison for GET and wildcard conditions.
4. For a matching validator, return a bodyless 304 with the relevant ETag/cache metadata. Do not stream the file or attach an error body. The browser combines it with its cached representation.
5. For changed content, send 200, current metadata and body. Never answer 304 for a missing file, failed auth, dynamic recovery page or unknown/stale validator.

Representation-specific tags and `If-None-Match`/304 behavior are defined in [RFC 9110, conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2). Compressed and identity representations must not share a strong tag for different bytes. If content-encoding selection varies with `Accept-Encoding`, responses need the corresponding `Vary` behavior. Preserve ordinary browser gzip delivery and verify headers on 200/304; adding broad new encoding support is unnecessary for this facelift.

Do not add a HEAD route solely for this stage; inspect and preserve current method support. Bound request-header parsing and response-header use within ESP-IDF limits. New headers must not exceed `max_resp_headers`, and any new routes must fit `max_uri_handlers` and be registered before the wildcard.

## Validators without expensive per-request work

Prefer build-generated content validators for immutable packaged files, computed from final bytes **after** tooltip substitution/minification/compression. Choose a compact manifest or sidecar design after measuring firmware RAM, SD reads and file-handle overhead; a full resident manifest and hashing a large asset on every request are poor defaults for this device.

Requirements for the chosen design:

- Distinguish logical URL, selected encoding and content bytes. A build ID by itself is not a content hash for arbitrary user-modified files.
- Carry validator metadata through manual/remote/OTA packaging and folder swaps, and invalidate any in-memory lookup on changes.
- Account for ordinary upload/delete/replacement paths. Missing/outdated metadata must fall back to a correct 200/no-cache response or recomputed trustworthy validator, never a false 304.
- Do not rely only on FAT timestamps plus file size: same-size rapid replacements can collide. Include this case in validation.
- Keep validator bookkeeping out of backup/export file selections and avoid shipping it as an unintended config file.
- Record steady/peak heap, added allocations, validator lookup cost and SD I/O. A 304 saves the response body even if a small metadata read remains necessary.

Stage 00b defines the format and implements a minimal generator/fixture integration; stage 01 emits compatible alternative assets, and stage 12 integrates the full release pipeline. The caching stage cannot be considered package-complete until that integration is verified.

## Update and compatibility behavior

Normal entry URLs should work without random cache-busting once revalidation is installed. Keep short content hashes for child assets and a versioned entry URL as recovery/migration for the previous firmware's already-fresh 12-hour HTML response. New server headers cannot invalidate a browser entry that has not contacted the server yet.

An open app may keep an old module graph across OTA; revalidation on a later navigation does not fix a missing lazy chunk in that already-open page. Preserve a controlled reload/recovery flow and drafts. Test a cached old entry, an open old page, new assets, deleted assets and rollback to legacy. Both UIs must survive the whole-HTML OTA replacement.

The alternative may declare a minimum compatible firmware/capability set for new APIs or cache behavior. If the installed firmware is older, offer a clear compatibility message or verified fallback; never pretend that an endpoint exists. Preserve `html/version.txt` as the legacy identity and keep alternative metadata separate.

## Small API extensions

Use existing APIs where they provide a clean, complete contract. Necessary focused additions are authorized when a gap materially affects parity, reliability or transfer cost. Candidate gaps include a small structured setup/system/capability snapshot, a structured directory/recognition response, or a validated configuration replacement operation. These are examples to evaluate, **not current endpoints or mandatory additions**.

For every addition:

- Record the concrete UI gap, request/response/error contract, auth, persistence/restart behavior, limits and firmware compatibility in document 03 and the stage handoff.
- Keep existing routes/payloads functional and avoid breaking MQTT/InfluxDB/Webhook/Home Assistant behavior.
- Keep request/response memory bounded; stream large content and avoid expensive repeated aggregation.
- Add focused firmware/contract tests and update frontend fixtures and capability handling together.
- Fit the appropriate stage: cache/status support early; save reliability during configuration; any further feature-specific gap when discovered. Do not repeatedly stop for approval solely because an agreed necessary change is firmware code.

An added configuration replacement route does not automatically guarantee atomicity across power loss. State precisely what validation/staging/rename/recovery achieves on FAT, and test claimed guarantees. Broader firmware restructuring, new product features and redesigning AP/USB provisioning remain separate scope.

## Required checks

- Unconditional GET 200; matching ETag 304 with zero body; changed content 200; weak/list/wildcard matching; malformed/oversized header handling.
- Gzip MIME/encoding and representation tags; unauthenticated conditional request; missing files; setup/error interception and transitions.
- Same-size rapid replacement, upload/delete, manual copying, stale/missing metadata, OTA swap and rollback; no incorrect 304.
- HTML/mutable/hashed/dynamic resource policies on both UIs, current header/handler limits and no cached mutations.
- Build and firmware resource impact, repeat-load bytes/request counts and actual spare-device checks. Do not report device verification before connecting/testing the spare ESP32-CAM.
